# 🎨 SVG DAX Engineering

One area of Power BI development I particularly enjoy is creating **custom SVG visuals directly from DAX**.

Instead of relying exclusively on standard Power BI visuals, SVG enables highly customized visual components that react dynamically to filter context.

### Examples

- Progress bars
- KPI cards
- Status badges
- Sparklines
- Navigation elements
- Rating indicators
- Variance arrows
- Mini bar charts
- Dynamic icons
- Goal trackers
- Conditional status markers
- Timeline indicators

### Example — Dynamic SVG Progress Bar

```dax
SVG_ProgressBar =
VAR TargetValue =
    [Target Sales]

VAR ActualValue =
    [Total Sales]

VAR Percentage =
    DIVIDE(
        ActualValue,
        TargetValue,
        0
    )

VAR ClampedPercentage =
    MIN(
        MAX(Percentage, 0),
        1
    )

VAR BarWidth =
    INT(
        ClampedPercentage * 100
    )

VAR FillColor =
    IF(
        Percentage >= 1,
        "%23217346",
        "%23E66C37"
    )

RETURN
    "data:image/svg+xml;utf8," &
    "<svg xmlns='http://www.w3.org/2000/svg'
          width='140'
          height='20'
          viewBox='0 0 140 20'>" &

        "<rect
            x='0'
            y='4'
            width='100'
            height='12'
            rx='6'
            fill='%23E0E0E0'
        />" &

        "<rect
            x='0'
            y='4'
            width='" & BarWidth & "'
            height='12'
            rx='6'
            fill='" & FillColor & "'
        />" &

        "<text
            x='108'
            y='14'
            font-family='Arial'
            font-size='10'
            fill='%23333333'>" &

            FORMAT(
                Percentage,
                "0%"
            ) &

        "</text>" &

    "</svg>"
```

### Why SVG DAX?

SVG allows Power BI developers to build visual elements that can:

- react to filter context;
- dynamically change color;
- display context-sensitive values;
- reduce dependency on custom marketplace visuals;
- support compact matrix/table designs;
- create unique dashboard experiences.

# 🧠 Semantic Modeling

A visually attractive dashboard is only as reliable as the data model behind it.

My preferred architecture is generally a **star-schema semantic model** with clearly separated facts and dimensions.

### Typical Architecture

```text
                Dim_Date
                    │
                    │
Dim_Customer ─ Fact_Sales ─ Dim_Product
                    │
                    │
                Dim_Region
```

### Modeling Principles

- Separate facts from dimensions
- Avoid unnecessary bidirectional filtering
- Prefer explicit measures
- Maintain consistent granularity
- Use dedicated calendar tables
- Reduce unnecessary columns
- Hide technical keys from report users
- Build reusable measure layers
- Maintain clear naming conventions
- Optimize cardinality
- Minimize model complexity

# 🎯 Dashboard Design Philosophy

A dashboard should answer questions, not simply display charts.

I generally design reports around the following hierarchy:

```text
1. What happened?
        ↓
2. Where did it happen?
        ↓
3. Why did it happen?
        ↓
4. What needs attention?
        ↓
5. What action should be taken?
```

### Design Principles

- Clear visual hierarchy
- Minimal clutter
- Consistent spacing
- Accessible colors
- Business-oriented titles
- Meaningful KPIs
- Controlled interactivity
- Logical drill paths
- Responsive navigation
- Consistent visual language
